Streaming temps réel

Crypto Streaming Pipeline

Un pipeline événementiel qui capte en continu les transactions BTCUSDT de Binance, les valide et les rend consultables en temps réel via une API et un tableau de bord.

Objectif

Le but n'est pas le trading. Les données publiques de Binance servent de source temps réel gratuite pour démontrer une architecture événementielle réutilisable.

La même chaîne s'applique à des cas industriels : logs machine, capteurs IoT, supervision de procédé ou monitoring de production.

Les données

Le flux public btcusdt@trade de Binance envoie chaque transaction au moment où elle a lieu, sans clé API. Chaque message contient le prix, la quantité, l'identifiant du trade et deux horodatages.

Dès la réception, ces champs bruts sont convertis en un format interne typé : le reste du pipeline ne dépend jamais du format Binance.

Architecture

  1. Binance WebSocketTransactions BTCUSDT en temps réel
  2. Producer PythonLecture du flux, mise en forme JSON, publication dans Kafka
  3. Apache Kafka (KRaft)Topic crypto-trades, découple la source du stockage
  4. Consumer PythonValidation des trades, rejets tracés à part
  5. TimescaleDBStockage time-series (hypertable PostgreSQL)
  6. FastAPI et GrafanaAPI REST et tableau de bord rafraîchi toutes les 5 secondes

Les étapes

  1. Ingestion. Connexion au WebSocket Binance avec reconnexion automatique en cas de coupure (délai qui augmente à chaque échec).
  2. Transport. Publication de chaque trade dans Kafka. Le prix et la quantité voyagent en texte pour ne perdre aucune décimale.
  3. Validation. Un trade est rejeté si le prix ou la quantité est nul ou négatif, si l'identifiant manque, ou si la paire n'est pas la bonne. Chaque rejet est enregistré avec sa raison et le message d'origine.
  4. Stockage. Insertion dans TimescaleDB sans doublons : si le consumer redémarre et relit un message, il n'est pas inséré deux fois.
  5. Restitution. Une API expose l'état du service, les derniers trades et leur nombre. Un tableau de bord Grafana, configuré entièrement par fichiers, affiche le flux en direct.

Ce que montre le projet

  • Ingestion temps réel robuste aux coupures réseau
  • Production et consommation Kafka asynchrones, sans Zookeeper
  • Insertion idempotente dans une base time-series
  • Contrôle qualité en ligne, avec un circuit de rejet traçable
  • API REST asynchrone avec pool de connexions
  • Tableau de bord et source de données Grafana décrits en code
  • Toute l'infrastructure lancée en une commande avec Docker Compose

Limites et suite

La V1 est volontairement simple et tourne en local. Elle n'a pas encore de registre de schéma, de tests de charge, de monitoring Prometheus ni de gestion de plusieurs paires.

La V2 prévoit une architecture hexagonale (logique métier séparée de Kafka et de la base), des tests unitaires, le multi-symboles et des métriques avec alertes.
